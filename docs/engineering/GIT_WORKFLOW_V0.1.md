# Giga Git & Pull Request Workflow v0.1

> **Status:** Proposed for joint approval · **Tracking:** [Linear 17T-18](https://linear.app/17thedev/issue/17T-18/w1-standardize-git-workflow-across-both-coding-agents) · **Applies to:** Trà, Thư and any development coding agents using this repository. Does not govern the customer-facing Giga Agent's GitHub tools.

## 1. Operating model

Use **short-lived feature branches off `main`**, one Linear issue → one working branch → one pull request. `main` is the canonical integration branch, never a daily development workspace. Both developers may work concurrently, but their agents must use independent checkouts or Git worktrees; never run two agents against the same mutable working tree.

- **GitHub:** code, reviews, canonical documents, CI and history.
- **Linear:** task ownership, reviewer, acceptance criteria, status and links to GitHub.
- **Review:** peer review by the other developer before merge, except an explicit, documented emergency override.
- **Merge strategy:** **Squash and merge** to keep one Conventional Commit per completed PR on `main`. Not every intermediate branch commit must be squashed manually.
- **Main safety:** no direct pushes, force pushes, resets or deletions by development agents. A successful PR review is necessary but not equivalent to authorization for the agent to merge.
- **Branch protection:** request human administrator to enable GitHub ruleset/branch protection for `main` and required CI checks. Instructions do not themselves enforce server-side restrictions.

## 2. Branch naming — strict

**Format:** `<type>/17t-<issue-number>-<short-kebab-slug>`.

Allowed `type`: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `ci`, `build`, `perf`, `revert`.

Requirements: lowercase ASCII, no spaces or accented characters, one 17T Linear issue ID, stable descriptive slug (2–6 words preferred), length ≤ 80 characters.

| Work | Correct | Wrong |
|---|---|---|
| Backend login | `feat/17t-21-login-api` | `my-branch` |
| Frontend chat | `feat/17t-22-chat-screen` | `thu/chat` |
| Agent fix | `fix/17t-31-agent-event-replay` | `fix_agent` |
| Cloud CI | `ci/17t-32-deploy-check` | `devops-work` |
| Documentation | `docs/17t-18-git-workflow` | `feature/NewRules` |

No developer name or AI product name in a branch: the **Linear issue** is its identifier. If an issue genuinely requires multiple independent PRs, open child Linear issues and use a new branch per independently reviewable unit, or document an exception before proceeding.

Historical branch names already merged are not retroactively renamed. New PRs follow the new policy.

## 3. Conventional Commits — strict

**Format:** `<type>(<scope>): <imperative summary>` (optional `!` before colon for reviewed breaking change).

- Allowed types are the same as branch types above. Use a meaningful lowercase scope: `api`, `web`, `agent`, `contracts`, `db`, `cloud`, `ci`, `workflow`, `docs`.
- Subject in English for consistent automated parsing, present-tense imperative, **≤ 72 characters total**, no trailing full stop. Prefer one semantic change per commit.
- Write a commit **body** for nontrivial rationale or tradeoffs. Optional footer `Refs: 17T-21`. Put issue ID in **PR body** at minimum.
- No messages like `update`, `fix stuff`, `commit by AI`, `work` or autogenerated meaningless descriptions.
- A breaking-change marker `!` does **not** waive API v1 compatibility. For frozen API changes follow ADR-001 and versioning first.

Examples:

```text
feat(api): add conversation listing endpoint
fix(web): handle stream disconnect during chat
refactor(agent): isolate tool execution from run state
test(contracts): cover unknown SSE events
ci(cloud): validate deployment workflow
docs(workflow): standardize branch and commit conventions
```

For PR titles use the **same Conventional Commit header**. The PR title becomes the squash commit subject on `main`; keep it accurate as changes evolve.

## 4. Safe branch lifecycle — development agent must follow

### Start (only if working tree is clean and target is an approved issue)

```bash
git status --short
git branch --show-current
git remote -v
git fetch origin
git switch main
git pull --ff-only origin main
git switch -c feat/17t-21-login-api
```

If the working tree has unrelated user changes, an unexpected branch, or a shared worktree, **STOP and report the situation**. Never run `git clean -fd`, `git reset --hard`, automatic `git stash`, or destructive commands just to make it clean. For simultaneous agents use independent clones or `git worktree add` on a new unclaimed path and branch.

### Implement and commit

```bash
git status --short
git diff --check
git diff -- apps/api
git add apps/api/src/auth.ts apps/api/test/auth.test.ts
git diff --cached --check
git diff --cached --stat
git commit -m "feat(api): add session login endpoint"
```

These paths are **examples**, not files known to exist. Stage **explicit paths**; avoid `git add .`, `git add -A`, committing untracked output, or sweeping unrelated changes. Do not add secrets, generated bundles or `.env` files. Respect existing user modifications.

### Publish and open PR

```bash
git push -u origin feat/17t-21-login-api
```

Open a PR **to `main`**, include the Linear issue `17T-21`, summary, changes, tests, API/DB/Cloud impact, screenshots/evidence when applicable, and reviewer. Start as Draft if unfinished. Use `.github/pull_request_template.md`.

### Keep up to date and handle conflicts

1. `git fetch origin`; inspect `git status`, base diff and PR status.
2. If the branch is behind `main` but no merge conflict and GitHub can merge, **do not rewrite history without need**; allow tested squash merge after approval.
3. If actual conflicts exist, agent must explain conflicting paths/owners, stop, and request a coordinated resolution. Only the owner may authorize integration/rebase of its own branch; *never force-push someone else's shared branch*.
4. Do not automatically `git pull --rebase` or `git push --force(-with-lease)`. On a shared branch, use a new PR or human-coordinated update, not silent history rewrite.
5. After resolving, rerun relevant checks and request re-review if substantive content changed. Never discard conflicting work or "pick ours" without reason and review.

### Merge and cleanup

- PR head and target reviewed, GitHub CI green, contract gate respected, human reviewer approves, deploy/security impacts explained.
- **Squash merge** with Conventional Commit PR title. The review/approval must be real; do not fabricate approval because an agent says it is complete.
- Only a human authorized to merge (or an explicitly authorized automation) may perform merge. After merge, move related Linear issue to Done if **all** acceptance criteria are met, not merely because the PR is merged.
- Delete only the **agent's own merged feature branch** after verification and authorization. Never delete or rewrite `main`, unmerged colleague branches or unknown worktrees.

## 5. PR / review rules

Each PR should be small enough to review and correspond to exactly one objective. Require:

- Linear `17T-N` issue ID, owner, intended reviewer and scope.
- Summary of behavior, changed files, test commands/results, tests not run.
- Explicit API contract / DB migrations / secrets / cloud deployment impact; add docs + ADR for architecture changes.
- Screenshots or safe logs for UI and cloud changes; no secrets or credentials.
- One peer review and passing applicable CI; no self-approved agent merges.
- State transitions on Linear are evidence-based: `Todo → In Progress → In Review → Done`.

### Required CI and repository settings

The proposed CI checks **branch format**, **PR title**, **matching issue ID in PR body**, and **Conventional Commit subjects** for non-merge commits in a PR (validate against base/head SHA). Separate build/test/contract checks should be required when added to the repository.

Human admin should configure main ruleset to require PRs, >=1 approving review, successful Git workflow check and applicable future test checks, no force pushes, and no delete access. Note that settings availability and effectiveness depend on GitHub permissions/plan; verify in the actual repo. A workflow file alone does not guarantee branch protection.

## 6. Scope ownership & two-agent concurrency

- `apps/api` and `apps/web` can evolve in parallel; `packages/contracts`, CI/infrastructure and `docs/architecture` require coordination.
- Shared contract changes: create contract PR/ADR first, review together, then implement client/server against approved contract. Never have two agents independently redefine DTOs.
- Do not share an active working tree between agents; use distinct clones/worktrees and avoid both editing the same file without coordinating through a Linear issue.
- Human author/reviewer separation is preserved even when an AI wrote most of a patch.

## 7. Handoff template

```text
Linear issue: 17T-N
Owner / reviewer:
Working branch / PR:
Changed paths:
Commit(s) / proposed squash title:
API, DB, Cloud & security impact:
Tests performed (commands + results):
Checks not performed:
Uncommitted/untracked files, conflicts, blockers:
Next action and who is authorized to perform it:
```
